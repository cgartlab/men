## 二、字体统一（OPPO Sans + Hack Nerd Font）

* **正文/标题一律 OPPO Sans**，`--font-serif` 令牌删除，字体栈里 OPPO Sans 之后只保留系统黑体（`PingFang SC / Microsoft YaHei / Noto Sans SC / system-ui / sans-serif`）——全站 0 处 `Georgia / serif` 引用。
  * OPPO Sans 只从**官方 CDN** 引用：其授权条款明确「不对字体进行改编或二次开发」「不向他方提供其他下载渠道」，因此**不得自托管、不得子集化**；官方 CDN 仅提供 Regular(400)/Medium(500) 两档 woff2（各约 744KB，覆盖 ~5000 常用字），600/700 由浏览器合成加粗，故层级以「字号 + 颜色 + 字重 500」为主。
* **代码/等宽字体 = Hack Nerd Font（MIT，可自托管）**：自托管**子集** `site/public/fonts/hack-nerd-font-{regular,bold}.woff2`，各 **75KB**（含拉丁 + 标点/箭头/制表符/电力线共 1125 字形）。
  * mono 栈第 2 位放 OPPO Sans：Hack 无中文字形，代码块里的中文注释因此落在同一族字体上，而不是各平台随机系统字体。
  * 若日后需要完整 Nerd 图标集，重新生成命令写在 `global.css` 字体块注释里（体积会从 75KB 涨到约 640KB/字重，按需取舍）。

## 三、排版实测优化（本次的主体）

### 3.1 事实审计（改前 → 改后）

| 指标 | 改前 | 改后 |
|---|---|---|
| 规则集命中总数 | **395 处** | **0 处** |
| 中文字号 < 13px 下限 | 46 处（最小 10.4px，导航 10.5px） | 0 |
| 中文负字距（汉字被挤压） | **154 处**（-0.01 ~ -0.03em，31 个选择器） | 0 |
| 小字对比度不足 | 40 处（最差 2.95:1） | 0（`tiny-text-audit` 342 个小字元素全过） |
| 正文行宽超标 | 最宽 **79 汉字/行**（956–1104px 容器） | 全部 ≤ 40 汉字/行 |
| 段落间距过小 | `step-card__desc` 0.29em | 0.86em |
| 标题层级倒挂 | `docs/index` h2 16px < h3 18px；`about` h1 30px = h2 30px；`index` 同页 h2 两种字号（20 / 35.2） | 每页单调：44/30/18、44/21/18 等 |
| 拓扑图标签**实际**渲染字号 | 桌面 **6.7–10.3px**、手机 **4.25–6.5px**（viewBox 1200 被压到 952/600px） | 桌面 ≥13.3px、手机 ≥12px，无溢出 |

### 3.2 关键判断（为什么这么改）

1. **中文行高比西文高一档**：汉字字身框占满，行距不足会「糊成一块」。正文 1.7→**1.75**，长文（≥100 字）**1.9**，大标题 1.2→**1.3**，区块标题 **1.35**，小标题 **1.4**。
2. **中文禁负字距**：`-0.01em ~ -0.03em` 的标题字距是照搬西文习惯，汉字占满字身框，负值直接挤压笔画。全站改为 **+0.01em**（标题）/ **+0.02em**（小字密集处）。
3. **小字档下限 13px**：原 `--font-size-eyebrow` 12px、`--font-size-eyebrow-nav` 10.5px —— 导航是中文（首页/角色/机制…），10.5px 的汉字属「看不清」级别，且它是全站出现次数最多的小字（62 处）。改为 13px 并保留旧令牌名作别名（不改 40 余处引用）。
4. **字号的模数级数**：`display 40–56 / h1 32–44 / h2 24–30 / h3 21 / h4 18 / h5 16 / body 16 / body-lg 17 / caption 14 / small(=eyebrow) 13`，相邻级比 ≈1.17–1.47，同页不出现后级大于前级。
5. **行宽用 em 不用 ch**：`ch` 按西文「0」宽度算，中文里 1 汉字 ≈ 1em。新增 `--measure-prose: 40em` 专管正文块（p/li/note/引用），**代码块与表格仍可用满宽**（它们有横向滚动/自身布局）。
6. **暖底上的弱化色**：`--color-fg-muted`(#737373) 在暖底 `#f0ebe2` 上只有 3.99:1（小字不达标）→ 暖底处一律换 `--color-fg-tertiary`(6.1:1) 或在暖底卡片上换同色相压暗版 `--role-*-text`（如「团队特性」2.95:1 → `--role-men-text` 4.4:1）。
7. **不用合成斜体**：中文没有真斜体字形，浏览器是剪切变形（糊笔画）。全站 `font-style: italic` 对中文内容一律取消。
8. **SVG 内文字按缩放折算**：拓扑图 viewBox 1200 单位被渲染成 ~1184px（桌面 0.99×）/ 1000px（手机 0.83×），`font-size` 必须乘这个系数才是实际字号。据此把容器放宽到 `--container-max`、`min-width: 1080px`，并把节点小字抬到 13.5px（实际 ≥13.3px），同时缩短过长标签（`si · 思考/知识管理` → `si · 思考`、`fresh-context 语义复核` → `fresh-context 复核`）、放大「兼 Judge」胶囊、窄屏隐藏最密两行。

## 六、追加（2026-10-10 晚）：字重「黑成一坨」根治 + 橘底改白字

### 6.1 根因：OPPO Sans 没有 600/700 真字面 → 浏览器**合成加粗**

合成加粗不是「更粗的字」，而是给字形描边加粗：汉字字腔（「门」「角」「色」「协」的内部空隙）
被填死。同串汉字 32px 的**墨量实测**（深色像素占比，越大越粗）：

| 情形 | 墨量 | 判定 |
|---|---|---|
| font-weight 400（正文） | 9.18% | 基准 |
| font-weight 500（**真 Medium 字面**） | 11.65% | 真字重 |
| font-weight 700（默认 → **合成加粗**） | **16.01%** | 比真 Medium 重 **37%** → 糊 |
| 700 + `font-synthesis-weight: none` | 11.68% | = 真 Medium ✓ |
| 700 + 字面声明 `font-weight: 500 700` | 11.38% | = 真 Medium ✓ |

### 6.2 修法（两个机制互为保险）

1. **`@font-face` 字重区间**（承重机制）：Regular 声明为 `300 400`、Medium 声明为 `500 700`
   —— 600/700 的请求直接命中 Medium 字面本身，在**字体匹配阶段**就不会触发合成，
   不依赖浏览器对 `font-synthesis-weight` 的支持。
2. **`html { font-synthesis-weight: none }`**（双保险）：实测同样有效（16.01% → 11.68%）。

副作用与对策：中文再也没有「粗体」这一层手段了（Hack Nerd Font 有真 700，拉丁标签照旧粗）。
`strong / b` 因此改成两层叠加：**真 Medium(500) + 颜色加深到 `--color-fg`**
（长文正文是 `--color-fg-secondary #404040`）。实测强调幅度 **+25.9% 墨量**（11.12% vs 8.84%）。
中文若还要更醒目，只能靠第三种手段（高亮底色 / 品牌色 / 下划线），属设计取舍，未擅自加。

### 6.3 橘底白字

`--color-accent-on-accent` 由 `#0a0a0a`（黑）改为 **`#ffffff`（白）**，配套把「承载文字的橘色填充」
统一换成 `--color-accent-soft #c94700`：

| 组合 | 对比度 | 结论 |
|---|---|---|
| 白字 on `#c94700`（新的橘色填充） | **4.79:1** | ✓ 达小字 AA |
| 白字 on `#e85d04`（原主橘） | 3.50:1 | 只够大文本 → 不再用于承载文字 |
| 白字 hover（填充压暗 12%） | 5.90:1 | ✓ |

改动点：`.hero-cta--primary`（含 hover：原「混白提亮」会让白字掉到 3:1 以下，改为压暗）、
`.hero-version-badge`、`.skip-link`、`::selection`、拓扑图中枢节点 + 图例色块。
**装饰性**圆点 / 细线 / 竖条仍用亮橘 `#e85d04`（不承载文字，保留视觉身份）。
另外清理了 6 处把「橘底文字色」误用在浅底上的规则（`.btn:hover`、`.site-header__gh:hover`、
`.about-link:hover`、`.about-phil-num`、`.about-license-tag`、`.wave-task--depends`）——
那些位置的白字会是白底白字，全部改为 `--color-accent-dark`。

`contrast-check.mjs` 同步新增规则守卫：「白字 vs 橘色填充 ≥4.5:1」被钉住，填充色改回 `#e85d04` 即 FAIL。

### 6.4 视觉复核结论（截图 + 逐张评估）

- 首屏主标题：笔画清晰、字腔未填死，「中等偏粗」而非糊成一团 ✓
- showcase 卡片区：五级层级（大标题 / 彩色小标题 / 角色大字 / 正文 / 标签）一眼可辨 ✓
- 角色页大卡片：小标题（职责/技能/约束）、加粗条目、正文三层颜色+字重区分清楚，最小字号处笔画仍舒展 ✓
- 橘底按钮与徽标：白字清晰，橘色被识别为「压暗一档的橘红」，视觉身份未丢 ✓
- 依复核意见顺带调深两处过淡的小字：卡片底部约束小字、关于页版本/出品方元信息（`fg-muted` → `fg-tertiary`）

## 七、孤行（末行过短）专项排查

工具：`site/scripts/widow-audit.mjs`（`npm run check-widow`）——逐字测量**实际折行**后的每一行，
统计末行的可见字符数（不可见字符如 U+2060/零宽空格不计入）。判定阈值可调：`--min N`。

### 7.1 实测基线（16 页 × 桌面 1440 / 手机 390，参与判定的折行文本块 776 个）

| 判定标准 | 违规数 | 含义 |
|---|---|---|
| 末行 < **4** 字符（本次要求） | **187 处** | 去重后 136 个不同段落 |
| 末行 < 3 字符 | 70 处 | |
| 末行 < **2** 字符（= 孤字 / 只剩一个标点） | **11 处** | 中文排版真正要禁的「孤字」 |

违规最集中的三类：① 页脚隐私段（同一段落在 16 页 × 3 种容器宽下出现，共 **48 处**）；
② 普通段落末行 1–3 字（151 处）；③ 窄表格单元（<220px，25 处）。

### 7.2 CSS 能做到的（已实施）

`body { text-wrap: pretty; line-break: strict; }`（两个都是继承属性）：
- `text-wrap: pretty` 折行时避免末行只剩一个词；
- `line-break: strict` 中文禁则从严，禁止把 `。，、；：）」』` 甩到行首。

实测效果：**187 → 180（只修掉 7 处）**。

### 7.3 为什么 CSS 解决不了（结论性发现）

`text-wrap: pretty` 是按**词边界**工作的；中文没有空格分词，浏览器把一整行汉字视为极少数
「词」，算法没有可调整的断点 —— 实测对中文孤行几乎无效。CSS 也不提供「最后一行」选择器
（只有 `::first-line`），`hanging-punctuation` 又是 Safari 专属。**因此「末行 ≥4 字符」这条
硬标准，无法用任何一条 CSS 规则在全站达成。**

另外验证过并**否决**的方案：把末行粘在一起（`&#8288;` U+2060 WORD JOINER）——在 11 处
「标点被甩到行首」的真实段落上逐个加过，实测**一处也没有修好**（Chromium 在
`</code>` 这类行内盒边界处仍会断行），已全部撤回；不留无用不可见字符。

### 7.4 只剩三个可行方向（各自代价已实测/评估）

| 方向 | 能做到 | 代价 |
|---|---|---|
| A 逐处改文案 / 列宽 / measure | 可做到 **0** | 需改动你的正文措辞、表格列宽、页脚 measure；约 100+ 处；文案一改又要重做 |
| B 采用中文排版通行口径「禁孤字」（末行 ≥2 字且不得只剩标点） | 只剩 **11 处**，改动面很小 | 比「≥4 字符」宽松 |
| C 测量式自动修正器（首屏前 JS，实测原型 187→59） | 大部分自动消掉 | 会给段落文本写入不可见字符（影响复制粘贴）；窄表格单元（97px ≈ 6 字/行）仍做不到；未修完的 59 处含页脚段（`<details>` 折叠内容 `getClientRects()` 失效）与代码 token 邻接的尾巴 |

**注**：页脚那条隐私文案在 `<details>` 折叠态下也会被判为违规，但它**展开后**的折行与折叠态一致，
所以是真实缺陷（不是误报）；同时它是全站重复度最高的一条（48/187）。

### 7.5 执行结果（按方案 A「严格做到 0」）

**最终实测：`npm run check-widow` → 违规 0 处**（16 页 × 桌面 1440 / 手机 390，757 个折行文本块）。
起点是 180 处（去重 124 个段落）。

做法（两段式，可复用）：

1. **人来定措辞，机器判折行**。先试过「自动搜索最小改动」（在 DOM 上批量试 ±1 字/标点），
   124 段里只搜出 29 个「通过」的候选，但逐条审下来语义破坏严重
   （各司其职→各司职、是不是→不是、前端→之前端、并行→并且行），**该方案被否决并删除**。
   最终由人（+ 5 个并行子 agent）逐段拟定**语义不变**的最小改动，再用验证器判定。
2. **结构性修法优先**（不靠改文案的地方）：
   - 路由表短值列（关键词 / 验证方式）改 `white-space: nowrap` —— 这两列是「A / B / C」式短值，
     折行后末行必然只剩 1–2 字；表格外层本来就有横向滚动，单行化后结构性消除该类孤行。
   - 文档信息卡在 ≤720px 改为「标签在上、值在下」单列堆叠 —— 原来值列只有约 190px，
     `v0.6.1（2026-10-07 发布）` 这类会被挤成末行 3 字。

工具（已入库，可复用）：
- `npm run check-widow` → `scripts/widow-audit.mjs`：全站逐字测量折行，报告末行字符数（`--min N` 可调阈值、`--json` 出结构化结果）
- `npm run verify-widow-fix` → `scripts/widow-verify.mjs`：候选文案验证器，在已构建产物上做 DOM 替换，
  **不重建**即可判定某处改动在桌面/手机两端是否都达标（含 `mode:'html'` 处理带 `<code>/<strong>` 的块）

改动规模：**112 行**、涉及 18 个源文件；全部为语义不变的最小编辑
（加虚词/标点、`及→以及`、`后→之后`、`均→均为`、句尾无损扩写、个别语序微调），
