# si-content-write（内容写作）

产出结构化、可发布的文本内容。面向博客、技术文档、周刊、产品文档四类场景。

## 适用范围

| 场景 | 典型产出 | 对应模板 |
|------|----------|----------|
| 博客 | 技术博客、观点文章、教程 | 博客模板 |
| 技术文档 | README、API 说明、架构说明 | 技术文档模板 |
| 周刊 | weekly、周报、新闻摘要 | 周刊模板 |
| 产品文档 | 功能说明、更新日志、发布说明 | 技术文档模板 |

本技能只负责**写作产出**。信息搜集、规划拆解、视觉设计由其他角色负责。

## 不要触发

- ❌ **纯搜索任务** — 只要查信息不产出文章，用 xun-search / xun-rss-scan
- ❌ **纯规划任务** — 只做任务拆解不写内容，用 si-plan-compose
- ❌ **纯代码任务** — 改代码、写脚本、做实现，交给 ji
- ❌ **视觉设计** — 配色、版式、Token 定义，交给 yi
- ❌ **投资/评审决策** — 持仓分析、产物验收，交给 chi

## 触发词

中文：写作、博客、文章、文档、weekly、周报、周刊、技术文档、产品文档、写一篇、起草、润色、重写、内容创作

## 写作工作流程（step-by-step）

### 步骤 1：需求澄清

动笔前必须确认 5 件事，不确定就追问，不脑补：

1. **目标读者** — 面向谁（开发者 / 普通用户 / 管理层）？
2. **篇幅** — 目标字数或行数？（博客建议 500–2000 字，文档按内容定）
3. **风格** — 口语 / 正式 / 技术严谨？（本项目默认口语节奏）
4. **发布日期** — 有无时间约束？周刊类有固定节奏
5. **发布渠道** — 主站 / 内部文档 / 仓库 README？影响格式（Frontmatter、链接相对路径）

### 步骤 2：素材搜集

- 已有上下文 → 直接复用对话内容
- 需要外部信息 → 调用 **xun-search**（查资料）/ **xun-rss-scan**（扫订阅源）
- 需要历史结论 → 调用 **si-knowledge**（查 knowledge/ 沉淀）
- 素材不足时**停下追问**，不要凭记忆编造

### 步骤 3：结构规划

1. 先定**标题**（见 SEO 规范：H1 唯一、含关键词）
2. 再写**大纲**（3–7 个 H2/H3 节点）
3. 每个节点写**段落要点**（每段 1 个观点）
4. 大纲定稿后再进入起草，**禁止边想边写**

### 步骤 4：起草

- 按大纲逐段写，每段 ≤6 行
- 关键信息**加粗**，列表优先于段落
- 段落之间留空行，长列表按主题分段
- 先求完整再求精炼，第一稿不追求完美

### 步骤 5：事实核查

- 外部事实逐条核查，使用三级标注（见下文）
- 每个标注**必须附来源超链接**
- 无来源的事实默认标注 ⚠️，不能直接引用
- 核查由 xun-factcheck 流程辅助时，结果仍由写作端标注

### 步骤 6：格式检查（Pre-Commit Checklist）

对照下文 Checklist 逐项勾选。有未通过项必须修改后再落盘。

### 步骤 7：落盘

1. 确认目标路径（默认 `docs/`、仓库 `README.md`、或任务指定位置）
2. 使用 `write` 工具写入 `.md` 文件
3. **验证文件存在且非空**（read 或 Test-Path 确认）
4. 报告落盘路径 + 行数

## 文章结构模板

### 博客模板

```markdown
# <标题：含关键词，H1 唯一>

> 导语：2–3 行，说明读者能得到什么，不剧透结论。

## <正文 H2 一：背景/问题>

- 痛点描述
- 现状分析

## <正文 H2 二：方案/做法>

- 核心步骤（编号列表）
- 关键代码/配置（用代码块）

## <正文 H2 三：验证/结果>

- 效果数据
- 踩坑记录

## 结论

- 一句话总结
- 下一步建议

## 延伸阅读 / CTA

- 相关文章链接
- 行动号召（订阅 / 反馈 / 联系我们）
```

### 技术文档模板

```markdown
# <产品/模块名>

## 概述

- 做什么
- 解决什么问题
- 适用版本/环境

## 安装

- 环境要求
- 安装命令（完整可复制）

## 使用

- 快速上手（最小示例）
- 常用配置说明

## API 参考

- 接口签名
- 参数表（名称/类型/必填/说明）
- 返回值与错误码

## FAQ

- 常见问题 3–5 条
- 排错步骤
```

### 周刊模板

```markdown
# Weekly <N>：<一句话主题>

## 导读

- 本期 3 个要点，每条一行

## <分主题 1>

- 每条新闻：标题 + 一句话解读 + [来源链接]

## <分主题 2>

- 同上结构

## Top 链接

- 本周最值得收藏的 3–5 个链接
- 每条附一句话推荐理由
```

## 文风规范

- **口语节奏**，短句为主，不写长段落
- **关键信息加粗**，列表优先于段落
- **单段 ≤6 行**
- 不写水文，不堆砌形容词
- 长列表分段，段间加主题句
- 每段只讲一个观点，段落间有逻辑递进

## 事实核查三级标注

| 标记 | 含义 | 处理 |
|------|------|------|
| ✅ | 准确，有来源 | 可直接引用 |
| ❌ | 错误/不实 | 标注错误原因，不引用 |
| ⚠️ | 不确定/存疑 | 标注不确定性，建议替代来源 |

每个标注**必须附来源超链接**，无来源视为 ⚠️ 不确定。

## SEO 基础规范

- **H1 唯一** — 全文只允许一个 `#` 标题，即文章主标题
- **H2 含关键词** — 每个 H2 尽量自然嵌入核心关键词
- **alt 文本** — 图片必须写 alt，描述图片内容，含关键词更好
- **内链** — 正文至少 1–2 个站内链接，指向相关文章
- **URL slug** — 文件名/路径用英文小写 kebab-case，如 `weekly-2026-08-20.md`
- **导语含关键词** — 前 100 字出现核心关键词，利于摘要抓取
- **无空标题** — 每个标题下至少 1 句正文或列表，不出现孤立标题

## 项目规范参考

- **全员红线 #7**：写作产出必须遵循——粗体关键信息、emoji 标注状态、列表优先于段落、单段 ≤6 行
- **全员红线 #1**：完成=验证过的完成。产出 .md 文件后必须执行 `Test-Path` 确认文件存在且非空
- **写作前确认需求**（红线 #6）：目标读者、篇幅、风格、发布日期——信息不全先追问
- **事实核查**：引用外部信息必须走 xun-factcheck，三级标注 ✅/❌/⚠️ 附来源链接
- **结构检查**：产出 .md 文件需通过 verify.mjs 的 `structure` 检查（YAML frontmatter 合法）
- **event.mjs 审计**：重要写作完成事件用 `event.mjs append --type decision.made --subject <摘要>` 记录到 events.jsonl
- **CHARTER_CHECK**：si 角色 Clarification level=HIGH，需求模糊时阻塞并追问，不脑补
- **协作边界**：内容写作由 si 执行，代码实现由 ji 执行，视觉设计由 yi 执行

## Pre-Commit Checklist

- [ ] 观点有据（关键论断有来源或推理链）
- [ ] 来源可查（链接有效、标注完整，无来源的引用已标 ⚠️）
- [ ] 无空话（删掉修饰性、无信息量的句子）
- [ ] 格式合规（粗体关键信息、列表优先、单段 ≤6 行）
- [ ] H1 唯一，H2 层级正确（无跳级）
- [ ] 代码块完整可复制（无省略号、无截断）
- [ ] 标题与正文一致（不文不对题）
- [ ] 无拼写/错别字，中英文之间空格
- [ ] 图片有 alt，链接非死链
- [ ] 文件落盘为 `.md`，存在且非空
- [ ] 长度符合步骤 1 确认的篇幅约束
- [ ] 日期/版本号等时效信息正确

## Anti-Patterns

- ❌ **边搜边写** — 素材未收齐就动笔，导致返工
- ❌ **脑补事实** — 凭记忆写外部信息，不做核查
- ❌ **一口气写长段** — 超过 6 行的段落不拆，破坏节奏
- ❌ **全文无加粗** — 关键结论不突出，读者抓不住重点
- ❌ **标题党** — 标题与内容不符，损害可信度
- ❌ **不落盘** — 写完只贴对话，不产出 `.md` 文件
- ❌ **跳过检查** — 不跑 Checklist 直接交付，靠"应该没问题"
