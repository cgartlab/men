# xun-factcheck — 事实核查

本 skill 定义 xun 的事实核查流程，覆盖核查标准、来源优先级和结构化输出格式。

## 不要触发

- 用户只需要一个来源的信息（用 xun-search 即可）
- 用户要求 RSS 扫描（用 xun-rss-scan）
- 用户要求进行内容写作（用 ji-content-write）
- 用户要求本地知识检索（用 si-knowledge）

## 核查标准

### 逐条审查原则

- **每条事实独立验证**，不批量通过，不以"大多数对"推断"某条也对"
- 一条事实即使与其他事实高度一致，也必须有独立来源支撑
- 不同来源之间必须相互独立（不互为转载）

### 确认阈值

| 状态 | 条件 | 标记 |
|------|------|------|
| 确认 | ≥2 个独立来源一致 | ✅ 确认 |
| 待核实 | 仅 1 个来源，或来源质量不足 | ⚠️ 待核实 |
| 未找到 | 无任何可靠来源支持 | ❌ 未找到 |

### 独立来源判定

- 不同域名、不同编辑团队 = 独立
- 同一媒体集团旗下不同子刊 = **不独立**
- 转载/引用同一原始来源 = **不独立**
- 维基百科引用独立原始来源 = 可算作独立（但维基百科本身不算）

## 来源优先级排序

| 优先级 | 类型 | 可信度权重 |
|--------|------|-----------|
| 1 | 原始来源 | 高（官方文档、论文、原始代码、政府数据） |
| 2 | 权威媒体 | 中高（主流新闻、行业权威媒体） |
| 3 | 行业报告 | 中（白皮书、调研机构报告） |
| 4 | 二手来源 | 低（博客、论坛、社交媒体） |

**优先级 1-2 的双源组合可确认**，优先级 3 的双源组合标记为"待核实"，仅优先级 4 的来源不足以支持任何结论。

## 核查流程

```
1. 提取待核查事实清单
2. 对每条事实，执行多关键词搜索（参考 xun-search）
3. 收集 ≥3 个候选来源
4. 按来源优先级筛选，判定独立性
5. 逐条验证：对照 ≥2 独立来源
6. 标注置信度：✅ / ⚠️ / ❌
7. 输出结构化报告
```

## 输出格式

```
【检索结果】
1. <事实描述>
   - 来源 A：<链接>
   - 来源 B：<链接>
   - 对比结果：一致 / 部分矛盾 / 完全矛盾

2. <事实描述>
   - 来源 A：<链接>
   - 对比结果：仅单源

【来源】
- 来源名称 | <链接> | <时间戳>
- 来源名称 | <链接> | <时间戳>

【置信度】
- 事实 1：✅ 确认（2 个独立来源一致）
- 事实 2：⚠️ 待核实（仅 1 个来源）
- 事实 3：❌ 未找到（无可靠来源）

【摘要】
- <整体结论，不超过 3 句话>
```

## 禁止行为

- 不将"没有找到反证"等同于"已确认"
- 不以个人知识替代来源验证
- 不猜测缺失的信息
- 不将未经确认的信息呈现为事实

## 项目规范参考

- **全员红线 #1**：核查结论必须附≥2个独立来源链接，单来源标注"待核实"
- **全员红线 #6**：核查标准不明时向用户确认，不猜测核查范围
- **确认阈值**：≥2独立来源一致→✅确认 / 仅1来源→⚠️待核实 / 无来源→❌未找到
- **独立来源判定**：不同域名+不同编辑团队=独立；同一媒体集团旗下子刊=不独立；转载=不独立
- **依赖 xun-search**：事实核查基于 xun-search 的搜索结果作为输入
- **event.mjs 审计**：核查完成用 `event.mjs append --type decision.made` 记录到 events.jsonl
- **只读约束**：不修改源数据，不写文件到生产目录
- **CHARTER_CHECK**：xun 角色 Clarification level=LOW

## 与 xun-search 的协作

事实核查依赖 xun-search 的搜索结果作为输入。当需要额外搜索时，按 xun-search 的搜索策略执行，并遵循同样的来源优先级标准。
